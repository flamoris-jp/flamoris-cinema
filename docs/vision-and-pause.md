# FLAMORIS Cinema: 構想と休眠の記録

**決定日:** 2026-10-31  
**状態:** PAUSED / 構想保存中。実装・新しいレンダリング実験・外部連携拡張は停止する。  
**位置付け:** 将来の構想。ここに書かれたAIコントローラーやプロジェクト記述形式は**実装済みではない**。

## なぜCinemaを考えたか

出発点は、Glyphで文字を変形・移動させたハロウィン映像の実験だった。文字が蝙蝠へ変化して飛び去り、一つの「O」がカボチャとして残る。この一連の流れは、単なるキネティックタイポグラフィにとどまらず、**「形を使って出来事を表現する」**技術だった。

文字も図形も役者になり得る。形、動き、変形、時間、相互作用があれば出来事を表現できる。対象を文字に限定する必要はない。ただし、モーフィングの成功だけで汎用CGエンジンが完成したわけではない。

当初は「CGエンジンを作りたい」という着想だったのに、先に `flamoris-cinema` を作成し、Blenderの実装・描画テストから入った。そのため**目的（何を実現するか）と手段（何を接続するか）が逆転**した。今後は「映画を作る機能」の追加を目的とせず、以下の構想を判断の基準とする。

## Cinemaの中心となる構想

**Cinemaは、自然言語で表現された制作者の意図を読み取り、AIと人間が共有・再編集できる制作プロジェクトに記述し、実現に必要なツールと実行順序を計画するコントローラー。**

撮影・映画はその用途の一つであり、MV、文字アニメーション、抽象CG、短い演出、将来の映画などを対象とし得る。Cinema自体をBlenderの小型版や独自の総合モデリングソフトにする必要はない。

概念的な流れ:

```text
制作者の自然言語 / 意図
         ↓
シナリオ・場面・出来事の構造化（プロジェクト設計図）
         ↓
AIの実現計画（ツール選択、依存関係、手順、検証条件）
         ↓
Glyph / Blender / Generation / Kachinco 等の適切な実行系
         ↓
成果物・検証結果・制作履歴をプロジェクトへ紐づける
         ↺ 意図を保持したまま部分修正・再計画
```

### 意図と実行計画を分離する

- **意図（長く保持するもの）:** 作品の目的、場面、被写体、出来事、順序、感情、演出上の制約、人間の選択。
- **実行計画（置換可能なもの）:** どの制作ツールのどの機能を、どの順番で呼ぶか。素材の参照、処理条件、入出力、失敗時の方針。
- **実績（検証可能なもの）:** 実行したツールと版、生成した成果物の所在・識別子、成否、修正履歴、未解決の制約。

「蝙蝠が飛び去る」という意図を、実行系が変わったからといって書き換えない。Glyphだけで作れるならGlyph、空間・照明・3Dが必要ならBlenderを使う。後から速度だけ直すなら、可能な限り関連する工程だけを再実行する。**再実行可能性は目標であり、現時点では未実装。**

### 役割と所有権の案

| 要素 | 担当すること | Cinemaが奪わないこと |
| --- | --- | --- |
| Glyph | 文字・輪郭・ベクター・モーフィング | 独自文字形状の設計と出典 |
| Blender | 物体・空間・3D・物理・照明・カメラ・描画 | ネイティブのCG制作・編集機能 |
| Generation | 生成モデルによる素材制作 | モデル推論と生成アセットの責任 |
| Kachinco / KineticTypo | 編集、字幕、音、タイムライン、完成動画 | 編集プロジェクトの状態 |
| Cinema | 作品の意図、イベント、依存関係、ツール間計画と制作履歴 | 各ツール内部の全機能の再実装 |

Blenderの「必要なものだけ抽出する」とは、ソースコードの切り出しではなく、**必要な機能をAPI・アダプター・実行単位として利用する**という意味。Cinemaが持つべき情報と、各ツールを正本とする情報は分ける。ツール呼び出しには、許可された操作、入力検証、資源制限、人による承認の境界が必要。

## 例: ハロウィンの出来事

制作意図: 「HAPPY HALLOWEENの文字が蝙蝠に変形して飛び去る。『O』の一つだけがカボチャになって残る。」

AIと人間が共有する記述候補:

1. Scene: 暗い背景に「HAPPY HALLOWEEN」の文字がある。
2. Event: 文字の輪郭が蝙蝠へ連続的に変化する。
3. Event: 蝙蝠がそれぞれ異なる方向に飛び去る。
4. Exception / Event: 指定した「O」は飛ばずにカボチャになる。
5. Final state: 画面にはカボチャが残る。

この場面は**記述形式を検討するための例**であり、正式なJSON Schema、機能保証、作成済みのCinemaプロジェクトではない。必要なのは「存在」「変化」「運動」「相互作用」「時間」などを、AIが意味を失わずに保存できること。実行方法は後で決めてよい。

## 旧StudioのTimeline Designerから引き継ぐ発想

ChatGPT Libraryに保存された旧Studioバックアップ `flamoris_studio_src_20260923_164500.zip` の **Timeline Designer** には、作品・シリーズ概要、Rough Timeline、Section Detail / Script を記述し、`timeline/timeline_design.json` に保存する構想と画面があった。「編集データそのものではなく、作品の設計図を保存する」という考え方はCinemaの原型に近い。

Cinemaに引き継ぎたいのは、**AIが読めて人も直せる、持続的なプロジェクト記述**という思想。Studioの旧画面やJSONを、そのままCinemaの仕様として採用・移植することはまだ決めていない。旧バックアップは参照資料であり、このリポジトリへ複製していない。

## ここまでに実証したこと / していないこと

2026-10-31までに、このリポジトリにはポータブルなシーン・演技データ検証、球体の簡易挙動、Blenderとの限定的な入出力、Glyphの実形状・部品演技の取り込みが実装された。Blender 5.2.3のCPU/HIP描画、複数カメラ、3秒の「赤」の歩行、Flamencoからの描画とKachincoへの受け渡しなどが試験された。歩行は後ろ歩きに見える実験結果を含む。証跡と制約は [acceptance](acceptance.md)、[glyph performance](glyph-performance.md)、[architecture](architecture.md) に保存している。

**未実装:** 自然言語から作品を構造化するAI、汎用イベント記述形式、ツール選択・組み合わせのプランナー、実行結果を伴うプロジェクトの部分再計画、汎用CG/映画の自動制作。既存のScene/Take JSONを、この将来の上位プロジェクト形式と混同しない。

停止前に策定した短編「赤、転ぶ。」や段階別の具体的な工程は[旧ロードマップ](roadmap.md)に**履歴として**残すが、現在の優先順位ではない。

## なぜ停止するのか

現段階のFLAMORISでは、汎用AIコントローラーを運用するためのプロジェクト記述・ツール境界・検証方法がまだ十分に固まっていない。機能先行の開発を続けるより、最初の着想と既存の成果を保存し、必要になった時に再評価する。

**休眠の具体的な扱い:**

- このリポジトリは改名・削除・アーカイブせず、コードと検証済み成果を保持する。
- 新機能、追加撮影、統合テスト、運用系の変更をこの判断だけで開始しない。
- この「停止」は**開発計画上の停止**であり、Blender / Flamenco / MCP / GPUサービスを停止する命令ではない。
- README・この構想・過去の契約・検証記録を残し、AIや人間が途中から読んでも出発点がわかる状態にする。
